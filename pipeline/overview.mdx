NanoJev is a 0.6B parallel decision model built on Qwen3-0.6B. Starting from raw programmatic targets and ending with a deployed checkpoint, the full pipeline proceeds through five clearly separated stages: you define questions with known probability distributions, build and assemble JSONL datasets, fine-tune the backbone with distribution-matching losses, extend the model with navigation data, then evaluate checkpoint quality and serve batched decisions over a persistent HTTP endpoint. No teacher API calls, chain-of-thought generation, or automatic candidate truncation are involved at any stage.

<Steps>
  <Step title="Define questions and target distributions">
    Each JSONL training record contains a `state`, a `questions` map, a `split` assignment, and a `gold_probs` field that carries the target probability distribution. The distributional target may be a one-hot deterministic truth, a known conditional event probability, or a uniform-over-optimal-actions policy target. Records are grouped by `state_id` and `metadata.source_group_id` to ensure related variations stay in the same split. Supported splits are `train`, `dev`, `calibration`, `test`, and `ood`.
  </Step>
  <Step title="Generate and assemble the dataset">
    Three generators produce support decisions, workflow tasks, and game states:

    ```bash
    python scripts/build_toy_decisions.py --output-dir data/support --seed 17
    python scripts/build_workflow_decisions.py --output-dir data/workflows --seed 20260917
    python scripts/build_game_decisions.py --output-dir data/games --seed 17
    ```

    After combining the split files for each source into `all.jsonl`, the assembler merges them, checks state and source-group separation, and writes `data/base_dataset/merged.jsonl`. The default generators produce **2,312 states and 6,936 questions**. Use `--validate-only` to run a schema audit before loading a model.
  </Step>
  <Step title="Train the base model">
    Fine-tune Qwen3-0.6B from the pinned revision using distribution cross-entropy losses. The key architectural and objective flags are `--set-head attention` for the Choice set-attention head and `--objective gold_distribution` for distribution targets. A short head-only warmup phase precedes full model updates:

    ```bash
    CUDA_VISIBLE_DEVICES=0 python scripts/train_pipeline_decisions.py \
      --input data/base_dataset/merged.jsonl \
      --output-dir runs/base_run \
      --model Qwen/Qwen3-0.6B \
      --revision c1899de289a04d12100db370d81485cdf75e47ca \
      --objective gold_distribution --set-head attention \
      --seed 17 --head-steps 12 --steps 600 \
      --batch-questions 12 --microbatch-questions 4 \
      --max-microbatch-tokens 6000 --max-length 512 \
      --eval-every 50 --precision bf16 \
      --backbone-lr 2e-5 --head-lr 2e-4 --head-warmup-lr 1e-3
    ```

    The trainer selects the checkpoint with the lowest dev target cross-entropy and evaluates it on all remaining splits after training.
  </Step>
  <Step title="Extend with navigation data">
    Generate a separate navigation dataset that excludes every map already seen in the game data, then continue training from the base checkpoint. The default navigation generator creates **500 maps, 3,000 states, and 9,000 questions** across four grid-representation views: `coords_multi`, `ascii_multi`, `coords_single`, and `ascii_single`.

    ```bash
    python scripts/build_navigation_v3.py \
      --v2-input data/games/all.jsonl \
      --output-dir data/navigation --seed 20260918

    python scripts/assemble_navigation_v3_views.py \
      --canonical data/navigation/all.jsonl \
      --labels data/navigation/all.jsonl \
      --replay data/base_dataset/merged.jsonl \
      --output-dir data/navigation_views --seed 17
    ```

    Continue from the base checkpoint with `--init-checkpoint runs/base_run`. The coordinates view provides explicit agent, goal, and wall coordinates alongside the full indexed grid. The ASCII view presents only the grid characters.
  </Step>
  <Step title="Evaluate and serve">
    Offline prediction metrics (cross-entropy, Brier score, ECE, TV, KL) are computed from the saved `predictions_*.jsonl` files. Closed-loop navigation benchmarks run the model as a controller for up to `2 × size²` steps per episode. On the 40-map navigation benchmark (T=1 probability sampling), NanoJev achieves 19/20 on 4×4 test maps and 18/20 on 6×6 OOD maps.

    The persistent serving script loads a checkpoint once and accepts repeated batched requests:

    ```bash
    CUDA_VISIBLE_DEVICES=0 python scripts/serve_decisions.py \
      --checkpoint-dir runs/navigation_run \
      --web-root web --host 127.0.0.1 --port 8765 --precision bf16
    ```
  </Step>
</Steps>

## Architecture choices

**`--set-head attention`** equips Choice questions with a shared scalar head and set attention. Boolean questions use a single-path sigmoid. Score questions read their ordered level descriptions independently and return the expected index. These head types are fixed at initialization and preserved across checkpoint warm starts; they cannot be changed when continuing from an existing model.

**`--objective gold_distribution`** uses the per-question cross-entropy against `gold_probs` as the training signal. Each question has equal loss weight. The complete candidate set shares one normalization denominator; padding never enters the loss. The gradient reduces to `p_i - q_i` after softmax normalization, making the target recoverable directly from the backward pass.

## Starting from the published checkpoint

The released model and dataset are publicly downloadable from HuggingFace. You can use them as a starting point to skip the base training stage, validate the data format locally, or fine-tune on your own programmatic targets.

- **Model:** [C-Tianyu/NanoJev](https://huggingface.co/C-Tianyu/NanoJev)
- **Dataset:** [C-Tianyu/NanoJev-Data](https://huggingface.co/datasets/C-Tianyu/NanoJev-Data)

The dataset provides `stage1/all.jsonl` and `stage2/all.jsonl` with their existing split assignments. Both files use the same training record schema described in the [Dataset Format](/pipeline/dataset-format) page.
